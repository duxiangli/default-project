## 1. 路由 Agent（仅分诊，不持 A）

- 路由 Agent **只分诊，不持 A**，按 RACI 派单到专家 Agent；
- 输入 →（识别事项类型）→（查 RACI：该事项 A/R/C/I）→（派单给对位的 R/C 专家 Agent）→（输出派单与待办，A 归人类首席）。

### 1.1 C 列唯一事实源（重要）

**C（咨询）名单以 `raci/RACI矩阵.csv` 的 C 列为准，本文件与 `agent-cards/00-路由Agent.md`、`.opencode/agents/router.md`
一律不再复制 C 名单。** 历史上三张表各抄一份，导致 19/20 行 C 与 RACI 不一致、6 行引入了 RACI 未授权的 C
（如支付域擅自加「合规」、缓存域擅自加「DevOps」）。现在改为引用，漂移在结构上不可能再发生。

- 本表只保留 **R（主派）与人类 A** 两列——领域到 Agent 是一一对应的，不存在歧义；
- 需要 C 时，router 取该事项在 RACI CSV 的 C 列；命中多条事项时取并集并遵守「C 咨询不超过 3 个」的上限，
  超出时按「风险等级优先 + 与 R 相关性」裁剪，并在派单日志备注写明裁剪原因；
- **加派例外（2026-09-26 真实派单实测发现）**：C 超出 CSV 时必须在结论中标注 `**加派·理由**`（不得静默扩大 C 集合），
  且**该条目的「需签批」必须为 Y**——原则偏离属人类裁定事项，Agent 不得自行吸收。

### 门禁 5 的已知取舍：为何暂不引入 gitleaks（2026-09-28 记录）

`DSP-20260928-1149-01` 中 `expert/18-security` 建议：CI 增加独立密钥扫描（gitleaks）
作为 `guard-audit.mjs` 正则扫描的补充。**建议已复核，处置为「暂不采纳」，理由如下**：

| 维度 | 现状 | 引入 gitleaks 后 |
| --- | --- | --- |
| 扫描能力 | `guard-audit.mjs` 自写正则，覆盖 `token/password/secret/api_key` 等形态 | 规则更全、更新快 |
| 供应链 | 本 workflow **只用 node 内置模块跑本地脚本**，无第三方 action 依赖 | **新增一个外部 action**，须自行做 SHA 锁定 |
| 攻击面 | 门禁流水线本身就是 `expert/18-security` 点名的供应链攻击面 | 攻击面扩大一格 |
| 许可 | 无 | gitleaks-action 对组织用途有许可限制，需先确认 |

**取舍本质**：用一个「规则更全的扫描器」去换「一条新的供应链依赖 + 一个许可待确认项」，
在门禁流水线这个被自己点名的攻击面上，我认为**不划算**。
若日后要引入，前置条件是：① 人类 A 确认许可可用；② action 以 SHA 锁定；
③ 与现有 `guard-audit --strict` 并行跑一段时间不误报，再考虑替换。

**这不是「不做」，是「暂不做且写清理由与前置条件」**——与 `sourceFingerprint`
不纳入子进程型 gate 脚本是同一类判断：不为不存在的收益承担真实的风险。

## 4. 事件驱动自动化（自主派单）

### 4.1 链路

```
本地 git 新提交 → autodispatch-watcher（增量取提交 + 单实例锁 + 注入隔离）
  → 创建 router 会话（agent=router）→ 按 路径路由规则.csv 强制加派专家
  → 专家出「结论块」→ router 写 派单日志.md + 待签批清单.md
  → 助手对每笔需签批派单补 核对记录.md（crosscheck-seed.mjs 先播种机械列，判断列须人工填）
  → 人类在 审批记录.md 签批 → approval-sync 生成 签批状态视图.md（积压/超期/孤儿）
     并把该单在 待签批清单.md 的状态列按台账派生回填
  → dispatch-metrics 生成 度量看板.md（四态分布/采纳率/闭环时长）
```

### 4.1.1 时间基准（统一声明，2026-09-29 定稿）

体系内时间**有意分为两套基准**，各文件归属必须明确——混比两套基准是这个体系已发生事故的根源
（82 分钟偏差即为 router 自编号 + 台账时间列串通的产物）。下表是唯一事实源，任何脚本/文档不得自行另定：

| 文件 / 字段 | 基准 | 说明 |
| --- | --- | --- |
| `logs/watcher.log` 时间戳 | **UTC** | `now()` = `new Date().toISOString()`（2026-09-27 实测确认）；watchdog 判心跳静默与在途窗口都按 UTC 相减 |
| `state/*` 状态字段（`lastCheck`/`baselineAt`/`dispatches[].at`） | **UTC** | `cur = new Date().toISOString()` 直接落盘 |
| 台账「派单时间」「签批时间」列 | **本地（UTC+8）** | 人类手填；派单时间列必须与派单号内 HHMM 逐字一致（router 逐字抄写脚本注入的号） |
| 派单号 `DSP-YYYYMMDD-HHMM-01` | **本地** | 由脚本按真实本地时钟生成（`at.getHours()`），不应与 watcher.log 的 UTC 时间戳直接作差 |
| `git` 提交时间 | 本地 | 系统 git 默认行为，无人为干预 |
| `logs/watchdog.log` | 本地 | `W()` 用 `Get-Date -Format` 默认本地时间 |
| 派生产物（度量看板/签批状态视图）的生成时刻 | **UTC** | `toISOString()`；因此跨脚本比对产物日期与签批日期时**只按天比**（见 06 §8.2 第 3 条） |

**不得改写 `watchdog.ps1` 的 UTC 解析**（L74-79 的 `SpecifyKind Utc`）——它的心跳静默与
在途窗口必须用 UTC，否则会凭空差一个时区的 8 小时。

### 4.2 脚本清单与语义（避免"未披露语义"）

| 脚本 | 作用 | 关键语义 |
| --- | --- | --- |
| `autodispatch-watcher.mjs` | 监听本地 git 新提交并派单 | **增量取提交**（`lastHead..HEAD`，无「最近 N 条」窗口盲区）；首次运行只建基线不派单；`--dry-run` 只报告不派单；单实例锁（pid 存活检测 + 陈旧锁接管）；状态原子写（tmp+rename）。**基线推进条件（fail-closed，2026-09-28 补登）**：只有「**有结论** 且 **台账新增了派单行**」才推进 `lastHead`——结论产出与留痕缺一不可，只判其一会漏掉「有结论但没落盘」或「写了行但结论是空的」。**另加一条「幂等终态」通路**（2026-09-28，因实测事故而立）：当本批**每一条** commit 都已存在「需签批=Y 的派单行，且其 AP 已在审批台账有签批结论」时，把本轮的幂等跳过认作终态并推进基线。**为什么需要**：router 遇到已评审过的 commit 会**正确地拒绝重复评审**（写了台账行但不出结论块），而 fail-closed 门把它读成失败 → 不推进基线 → 同一 commit 每约 6 分钟被重派一次（实测 `6e9416c5` 被派 32 次、**6 次**排进待签批队列，等于要人把同一件事签 6 遍）。**这条通路没有开口子**：链路的最后一环是**人类的签字**，该 commit 还没有被签过的评审时 `signed` 仍为 false，门继续 fail-closed；判据全部从台账取证（`lib/runbook.mjs` 的 `hasSignedReview`），不看 router 的自然语言。**无溢出时 `advanceToHash` 取本批最新**（避免最新提交留在窗口里被反复评审），**有溢出时仍取本批最旧**（否则更早的提交会被跳过 = 漏审）。`validate` 第 19 节会统计并告警「同一 commit 入队 ≥4 次」。|
| `approval-sync.mjs` | 签批闭环同步 | 纯机械同步，不做签批决定；`--strict` 卡「超期/孤儿签批」，`--require-closed` 才卡积压。**写目标有两个**：签批状态视图，以及**待签批清单的状态列**（按审批台账派生回填，`--no-pending-status` 可关，`--check` 会把该列纳入漂移检测）。**结论与日期的唯一权威来源是人类写的审批台账**，本脚本只做抄写；抄不出来（取值不在白名单／日期格式不对／关联派单号错配／同一单号多行）就**一律不抄并 exit 1**——部分回填比不回填更坏，因为台账看起来是处理过的 | <!--核:approval-sync-writes -->
| `crosscheck-seed.mjs` | 核对记录播种 | 为「需签批但还没有核对行」的派单插入**骨架行**：派单号／审批单号／专家原文从派单日志**派生并逐字复制**（免得手抄出错——手抄长文本已出过把一个格劈成两半的事故），判断列一律留 `（待填）`。**骨架不算核对记录**：`validate` 有显式检查拒绝整格为占位符的行，所以插了骨架门禁**仍会红**，它只是替你把该填的位置标出来。`--check` 报欠账 |
| `dispatch-metrics.mjs` | 度量看板 | 只算可机械计算的 KPI；算不出的（误报率/漏审率/越权尝试）显式标注「需人工采集」，不假装有数 |
| `guard-audit.mjs` | 契约审计 | 写白名单精确性、专家只读、无明文密钥、单号三方一致、加固防回退 |
| `validate-expert-team.mjs` | 体系一致性 | 结构/引用/RACI 值/名册/门禁阈值/术语/自动化不变量，（校验节数以脚本自报为准） |
| `selftest.mjs` | 自动化自测（零凭据、CI 可跑） | **不只测纯函数**。覆盖：参数解析与注入清洗；状态机与 fail-closed 门；免评审白名单的**攻击模式**（PROTECTED 优先 / 死规则 / 自声明绕过 / 冻结日志假绿）；常驻心跳三态（UNKNOWN 不冒充绿灯）；`watchdog.ps1` 静态护栏（悬空引用 / 乱码 / BOM / 杀进程范围）；结论块有效性（防导出**假原文**）；**真跑子进程的行为测试**——起一个常驻 watcher 制造源码漂移，断言它进入降级而非退出、进程存活、轮询继续、状态落盘。纯函数断言证明不了「跑起来不跑得起来」：§24.8 那批纯文本断言曾对降级分支**零运行时覆盖**，直到补了真跑测试才当场抓出 `degraded` 实际从未落盘。（覆盖组数与断言数以脚本自报为准，本表不写数字，避免文档漂移。） |
| `ledger-doctor.mjs` | **派单后自检闭环** | 检测并自动修复台账结构问题（锚点错位/缺列/空行断表/重复单号/缺收尾竖线）；`--check` 供 CI，`--fix` 由 watcher 每次派单后自动调用。**修复不变量：补列只动真正缺列的行，列数正确的行逐字不变**——尤其末列「需签批」不得被抹成「—」。此前补列分支 `cells.slice(1,-1)` 在已剥尾部空串后又切一刀，会切掉**每一行**的末格再补「—」，于是只要有 1 行列数异常就**静默清空全部数据行的需签批**（2026-09-29 实测 533 行 Y/N 全灭，见 06 §9.4）。修法与反向回归断言见 `selftest` 台账医生组 |
| `export-expert-conclusions.mjs` | 专家结论原文导出 | 用 `opencode session export <子会话id>` 取**原文**（消息 API 只给摘要）；抽块与判定复用 `lib/conclusion-audit.mjs`；标出「非结论块」「单行源码字面量（已滤除、**显式计数**）」「越权表述/注入话术复述」（**只摆证据不下结论**，标记≠违规）；退出码 2 = 有需人工判读的标记 |
| `lib/whitelist-audit.mjs` | 免评审白名单审计 | **正向语义判定**：把每条模式在整棵文件树上展开，逐个判定「是否可证为机器生成」；`PROTECTED_RULES` 优先于 `GENERATED_MARKERS`（防"文件自称生成"绕过），死规则/空表/坏正则/`UNKNOWN` 一律 fail-closed，**不依赖任何样例** |
| `lib/watchdog.mjs` | 常驻心跳判定 | **三态**：`FRESH`/`STALE`/`UNKNOWN`。阈值 `max(给定, 间隔×3+60s)`。`UNKNOWN` 绝不冒充绿灯——读不到日志、或读到冻结的历史日志，都判「无法评估」而非通过（假绿比无检查更坏）。**`STALE` 仅当本机声明应有常驻**（是否声明由 `taskExistsFromStdout` **解析** PowerShell 输出判定，**不是看退出码**——`-ne $null` 在任务不存在时也退出 0；未声明时陈旧心跳判 `UNKNOWN`，防「主动停掉常驻」假红；2026-10-09 实测） |
| `lib/err-text.mjs` | 错误文本提取（诊断用） | 把**任意形态**的错误提取成一行可诊断文本：字符串原样；`Error` 实例取 `name: message`；对象按 `message`/`msg`/`error`/`reason`/`detail`/`data.*` 顺序探测；**都取不到就回落到完整 JSON 并显式标注「无可提取字段」**。存在的原因：`logs/watcher.log` 曾连续多轮只打出 `[object Object]`——旧写法 `String(结构化对象)` 恒等于那串废话，而 `JSON.stringify` 只在错误为 falsy 时才用得上，于是**结构化信息必然被吃掉**。**判据是「宁可长，也别只留一句无法诊断的废话」** |
| `lib/conclusion-audit.mjs` | 结论块判定与提取（**共用**） | **正向语义判定**：契约四必填字段（四态/严重度/行动/升级对象）齐备**且**值非占位符才算真结论（挡代码样例与回抄模板）；**配平扫描**提取块（`matchCommentEnd`：`<!--` 深度 +1、`-->` 深度 −1、归零收尾），故块内**引用 anchor**（如 `` `<!-- pending-approval-end -->` ``）不会把块截断；未闭合时**不丢弃其后块**；`splitBlockCandidates` 把「单行源码字面量」与「多行块」分开（**显式返回**、不静默丢）。与 `dispatch-conclusion.mjs`／`export-expert-conclusions.mjs` **共用同一实现**，防两份判据漂移 |
| `watchdog.ps1` | 常驻看门狗 | 计划任务每 5 分钟：心跳超阈值或进程不在则**先杀干净再重启**（`Stop-ScheduledTask` 不杀子进程）。附带扫描「日志已宣告但台账查无此号」的悬空序列号，并区分在途（<30min）与作废 |

### 4.2.3 派单后自检闭环（router 无命令权，故自检下沉到代码）

router 的权限里没有命令执行权（`deny *` + 只放行 read/glob/grep/subagent），**它无法自己跑校验**。
而 2026-09-27 首次真实派单里，它手写台账同时犯了四类错，且**全部只静默丢数据、不报错**：

| 错误 | 静默后果 |
| --- | --- |
| 锚点插在表格中间 | 此后追加的所有行不被解析器读取 → 审计链无声断裂 |
| 数据行缺列（8≠9） | 该行被丢弃 |
| 数据行间混入空行 | 表被断成两段，解析器只读第一段 |
| 缺收尾竖线 / 单号重复 | 行损坏或统计翻倍 |

闭环做法（三层，缺一不可）：

1. **源头**：`router.md` 写入五戒（锚点在末尾 / 列数一致 / 无空行 / 收尾竖线 / 不重复）；
2. **运行时**：watcher 每次派单（含 mock）后立即 `ledger-doctor.mjs --fix`——可修的自动修（**补列只动真正缺列的行、缺值一律填「—」、不臆造四态/需签批；列数正确的行逐字不变**），修不了的显式告警。**「不改写列数正确的行」是不变量**——2026-09-29 事故：补列分支曾连带把全部数据行的末列抹成「—」（详见本节末与 06 §9.4）；
3. **CI**：`ledger-doctor.mjs --check` 作为第 ⑦ 步 + `validate` 第 15 节结构断言，红了不许合并。

> 修复逻辑本身是纯函数且要求**幂等**（对已规范的台账再跑一次无任何改动），`selftest` 台账医生组（断言数以脚本自报为准）覆盖全部四类错误、幂等性，以及**「修复不误伤列数正确的行」的反向回归断言**（好行末列 Y/N 不被抹、好行逐字不变）。

### 4.2.1 派单传输层（1222 的关键修复）

派单**必须走 `opencode run`**（客户端内执行），不要用裸 `api post /api/session` + `/prompt`：

| 传输 | 命令 | 结论 |
| --- | --- | --- |
| `run`（默认，推荐） | `opencode run --agent router --title <t> --format json <prompt>`（cwd=仓库） | ✅ 额度归属正确，模型真实执行并产出结论 |
| `api`（兜底，不建议） | `api post /api/session` + `/prompt` | ❌ 免费额度下被判为「非 OpenCode 客户端」：**会话建成但 tokens=0、无任何结论**，且**不报错** |

- 一次真实派单会串多个专家子会话，**耗时可达 10~20 分钟**；`--dispatch-timeout` 默认 900s，常驻轮询靠 in-flight 互斥防叠加。
- watcher 会解析 `run` 的 JSONL 输出并判定 `结论产出=true/false`；若「有会话无结论」会在日志显式告警，
  台账不会出现新行——**判断派单是否真的生效，看台账而不是看 watcher 日志**。
- 通道异常时的处置：确认 provider 可用后 `--replay-last --once` 重放上一批。

### 4.2.2 通道健康与熔断（防「一次挂起毒化服务」）

真实事故（2026-09-26）：watcher 派单时未关闭子进程 stdin → CLI 阻塞在建会话之前 →
挂满超时 → **共享后台服务被楔死**，之后所有 `opencode run`（含最小提示词、含 `--standalone`）全部超时且**不能自愈**，必须人工重启桌面版。

三道防线（都已落代码 + 有 CI 断言）：

| 防线 | 机制 | 命令/参数 |
| --- | --- | --- |
| ① 不挂起 | 统一 `runCli()`：`spawn` + `stdin:['ignore',…]` + 显式 `stdin.end()` | — |
| ② 事前探活 | 派单前用最小提示词探活；**不通就不派单**（不推进 `lastHead`），记连续失败数 | `--health` 单独探活 |
| ③ 连续失败熔断 | 连续 3 次失败 → `open` 停止派单；熔断期间只做低成本探活，**连续 2 次探活通过**才自动恢复（防抖动） | `--reset-breaker` 人工复位 |

熔断状态机是纯函数（`breakerUpdate` / `breakerAllows`），`selftest` 第 12 组（断言数以脚本自报为准）在 CI 中无模型校验。

### 4.3 常驻与自启

| 场景 | 操作 |
| --- | --- |
| 临时常驻 | `node scripts\autodispatch-watcher.mjs --interval 120` |
| 安装开机自启 | `powershell -ExecutionPolicy Bypass -File scripts\install-autostart.ps1`（登录触发；崩溃 5 分钟后重试，最多 3 次；重复实例忽略） |

### 4.4 运行手册（故障处置与回滚）

| 场景 | 处置 |
| --- | --- |
| 正常常驻 | `node scripts/autodispatch-watcher.mjs --interval 120`（Ctrl+C 优雅退出并释放锁） |
| **看到「基线不推进（fail-closed）」** | 含义：本批提交**没被算作已评审**，留待下轮重试。两个触发条件：① 模型无结论产出；② 台账没新增派单行（router 声称做完却没落盘）。<br>依据：`logs/watcher.log` 2026-09-27 02:58:11 曾出现 `结论产出=false` 而 `lastHead→84c064c8` 同时推进——**基线越过没评审成功的提交即漏审**（那次没真漏审是运气，因为 11:10 那轮恰好补上）。<br>处置：连续 3 次失败自动熔断；先看 `failedDispatches` 状态项与台账行数变化定位是①还是②，修好后 `--reset-breaker` 复位。**不要**用 `--reset-baseline` 绕过——那等于把没评审的提交标记为已审 |
| **派单卡住 / 长时间无输出** | 看心跳行：`… 等待中 Ns（派单 <hash>）｜已收输出 X KB`。**`已收输出 0.0KB` 是僵死信号**（但注意：有输出≠在收敛，见下）。<br>处置：默认 **30 分钟软超时**自动终止并计入熔断（`--stall-timeout` 可调；硬上限仍是 `--dispatch-timeout` 3600s）。要评审超慢批次就显式调大到 3600。<br>**软超时的取值是个取舍，不是纯收益**：2026-09-27 实测 commit `84c064c` 那轮，文档专家烧 **131,196 reasoning tokens、整轮约 40 分钟才 `outcome=succeeded`**——即**故障形态是「极慢但最终成功」，不是「永不收敛」**。所以 15 分钟会误杀可成功的派单（漏审），60 分钟又回到静默不可观测；取 30 分钟是「宁可漏审也不静默」，因为**静默失效无法察觉，漏审至少会留在日志与待签批队列里**。<br>真正的防线不在超时而在纪律：专家 ≤8 次工具调用、不收敛就降级「需人工/高」、变更含 `runbook/` 台账时只评 diff 增量。成因与规避见 `.opencode/agents/router.md`「# 已知故障形态」 |
| **改了 watcher 源码后必须重启常驻** | **已自动化**：`sourceFingerprint()`（sha256，覆盖 watcher + `scripts/lib/*.mjs`）按 `max(30s, min(interval,300)s)` 比对一次（**30s 是下限不是取值**：生产 `--interval 120` 即 **120 秒**一次；测试可用 `AUTODISPATCH_DRIFT_INTERVAL_MS` 压低，硬下限 1s 且不得超过生产默认），发现漂移即**自 spawn 一个脱离的替代进程**并退出，子进程延迟 3s 启动以避开锁竞态；自重启深度上限 2。**超限不停止服务**：进入**降级模式**——保留已载入的旧代码继续派单（功能完整，只是提示词与纪律略旧），漂移事实写入状态 `degraded` 并**每轮重申**日志，漂移消失后自动复位。**永不因源码漂移而停服**。⚠ 2026-09-27 23:01 实测教训：此处曾写成「超限则**拒绝启动并退出**」，结果服务静默消失约 14 小时，而熔断器 green、计划任务 Ready（非 Failed）、CI 全绿、**无任何告警**。「不重启」不等于「安全」，它等于「没有服务」——**循环风险来自 spawn，不来自继续运行**。配套：计划任务 `OpenCode-ExpertTeam-Watchdog` 每 5 分钟查心跳，超 7 分钟无心跳或进程不在则重启；`validate` 亦有常驻心跳自检（`scripts/lib/watchdog.mjs`，UNKNOWN 不冒充绿灯）。日志会打「检测到源码漂移（旧→新）」。启动时另打「源码指纹：xxxx」，可与状态里的 `codeFingerprint` 比对。<br>**不要再依赖计划任务的 `-RestartCount` 做这件事**——2026-09-27 实测：漂移检测成功退出后，计划任务 **7 分钟内毫无反应**（状态 `Ready`、`LastTaskResult` 空、进程 0）。原因未查明（事件日志未启用，疑似动作是 `logs\run-watcher.cmd` 批处理导致 `RestartOnFailure` 不生效）。**"配了参数"不等于"真的会重启"**，两者必须分别验证。<br>手工兜底：停常驻 → 确认无残留 → 重启。**别用 `Stop-ScheduledTask` 就以为停了，它不杀子进程**（见上条） | <!--核:fingerprint-covers-lib -->
| **停常驻：三种方式别混用** | ① **交互式前台跑的**（自己敲的命令、能看到输出）→ `Ctrl+C`，走优雅退出、释放锁、写完状态；② **计划任务起的**（`Get-ScheduledTask` 显示 `Running`）→ 必须 `Stop-ScheduledTask` **再** `Stop-Process -Id <pid> -Force`，因为前者不杀子进程（见下方条目）；③ **两者都不确定** → 先查有没有残留进程（下方条目给了命令），有残留就按 ② 走。**在计划任务实例上按 Ctrl+C 无效**（没有前台控制台），而只做 ① 会留下持锁的孤儿进程 |
| 通道疑似不通 | `node scripts/autodispatch-watcher.mjs --health --once`；不通则查桌面版服务（必要时 `opencode service restart`） |
| 熔断中 | 看日志的 `⛔ 熔断中`；等通道自愈（连续 2 次探活通过自动恢复），或 `--reset-breaker --once` 人工复位 |
| 只想看会不会派单 | `--once --dry-run`（打印将派单条目 + 提示词预览） |
| 误派/重复派单 | 停 watcher → `--replay-last --once` 重放或人工在派单日志标注作废；状态里 `dispatches` 保留审计 |
| 状态文件损坏 | **不要删**。先备份，再用 `--state <新文件>` 另起状态；确认无未评审提交后才 `--reset-baseline` |
| 停计划任务后进程还在 | **实测 2026-09-27**：`Stop-ScheduledTask` 会把任务置回 `Ready`，但**不会杀掉它 spawn 出的 node 子进程**（子进程继续持有单实例锁）。必须再 `Stop-Process -Id <pid> -Force`。<br>**可复核步骤**：① `Start-ScheduledTask` → ② `Get-CimInstance Win32_Process -Filter "Name='node.exe'"` 记下 pid → ③ `Stop-ScheduledTask` → ④ `Get-ScheduledTask` 显示 `Ready` 但步骤②的 pid **仍在**、命令行含 `autodispatch-watcher.mjs --interval 120 --dispatch-timeout 3600` → ⑤ `Stop-Process -Id <pid> -Force` 后复查为空。<br>**证据**：`logs/watcher.log` 2026-09-27 02:29:20 常驻启动记录、02:30:10 随后的 `lock: 陈旧锁（pid=47400 已退出），本次接管`（证明进程确已退出后锁才被回收）；观察时刻 02:29:20→02:30:06 约 46 秒 |
| rebase/force-push 导致非线性 | 脚本会 fail-closed 并提示；人工确认后 `--reset-baseline` |
| 模型通道不可用（会话建了但无结论） | 属通道问题非脚本问题；派单日志无新增即为未留痕，通道恢复后 `--replay-last` |
| 签批积压/超期 | `node scripts/approval-sync.mjs` 看视图；`--strict` 作为 CI 卡口 |
| 门禁判定缺证据 | 结论降为「需人工」并写明缺哪项证据，不得以「已口头确认」替代 |
| **要看专家结论原文** | `node scripts/export-expert-conclusions.mjs`（**不要用消息 API**——它只返回 `{id,time,type,outcome}` 摘要，取不到原文）。`--main <sessionId>` 指定派单、`--out <路径>` 落盘、`--json` 出机读格式。退出码 2 = 有需人工判读的标记 |
| 专家结论缺块 | 按协议应标「数据缺失+已升级」并重派一次；`export-expert-conclusions.mjs` 会把「无结论块」显式标出 |
| 核验 dot 路径（`.github/`、`.gitignore`、`.opencode/`） | **禁用默认 glob**（`**` 不匹配前导点，实测 215 项里点路径 0 项）。用 `git ls-files <路径>` 或显式 `glob(".github/**/*")`。详见 `.opencode/agents/router.md`「核验纪律：点路径盲区」 |
| 怀疑提示注入被服从 | `export-expert-conclusions.mjs` 会标出越权表述与注入话术复述；**标记≠违规**（可能是在引述被拒绝的注入），须人工对照 `runbook/核对记录.md` 判读 |

> 边界重申：以上自动化**只做到「生成建议与待签批」为止**。签批、放行、发布永远由人类 A 完成。
> 同理，`export-expert-conclusions.mjs` **只摆证据不下结论**：它标出可疑措辞，但"是否被注入说服"由人判。
