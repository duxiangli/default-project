# 核对记录（专家结论 × 复核结论 双方核对台账）

> **本文件是「双方核对」的唯一落点。** 起因：2026-09-27 我把 `DSP-20260927-0040-01` 的专家结论复核为
> 「部分不成立」，但**没有同时保留专家的原话**，导致台账里专家的有效发现被我的复核叙述盖掉——
> 而实际上「交付包未含 CI 与 .gitignore」**就是成立的**，「仓库里有」与「包里有」不是同一件事，不能互相否证。
>
> 因此定规矩：**专家结论与复核结论必须并列记录、不得互相覆盖。**

## 核对五律

1. **原话留存**：`专家原始结论` 列必须是**专家自己写的原文**。
   取法按优先级：① `node scripts/export-expert-conclusions.mjs`（导出子会话全文里的结论块，**权威来源**）；
   ② 退而求其次才引 `派单日志.md` 该行结论摘要（那是 router 的二次概括，**不得冒充专家原话**，引用时须标明"引自摘要"）。
   历史遗留行凡标「引自摘要」的，其效力弱于原文行——两者冲突时以原文为准。
2. **不成立须附反证**：复核结论判为「不成立」时，`可验证反证` 列必须给出**能被别人复现的证据**
   （文件路径 + `git ls-files` 结果 / 校验脚本输出 / 可重跑的命令）。
   **只陈述相反事实不算反证**——例如"仓库里有这个文件"不能证明"包里有这个文件"。
3. **部分成立要写清差在哪**：拆成「成立部分」与「不成立部分」两句写，差集必须具体到对象与位置。
4. **条件与处置独立成列**：整改动作写 `处置` 列，不混进结论判断。
5. **强制对账**：每条 `需签批=Y` 的派单行都必须在本表有对应行（`validate` 第 16 节强制检查）。
6. **「工具查不到」≠「不存在」**（2026-09-27 `DSP-20260927-0040-01` 三轮误判换来）：
   断言任何文件/资源「缺失」前，必须先排除**工具自身盲区**，并在 `复核方式` 列写明是怎么排除的。
   已知盲区：① `glob` 默认 `hidden:false`，`**` 不匹配前导点 → `.github/`、`.gitignore`、`.opencode/` 一律查不到；
   ② Node `fs.globSync` 不支持 `dot` 选项（只有 tinyglobby 才有），**换 flag 无效**，只能用显式点路径模式或 `git ls-files`；
   ③ 子会话消息 API 只返回摘要（`{id,time,type,outcome}`），读不到专家结论原文 → 用 `opencode session export <子会话id>` 导全文。
   **同时也要防反向失效**：不能因为"工具有盲区"就把任何缺失指控一律判为成立——仍须给出可复现的核验方式；
   ④ **常驻进程跑的是启动时载入的代码**：`autodispatch-watcher.mjs` 是 ESM，改了源码不重启，常驻会一直用旧逻辑派单且**无任何提示**。核验办法：从进程命令行取提示词文本、grep 新纪律关键词（如 `C 列只填`、`派单号（脚本已按真实时钟生成`），grep 不到即旧代码。2026-09-27 我因此差点误判"修改无效"。
   ⑤ **`runCli` 曾把 `timedOut` 恒写 `false`**：超时分支只 `p.kill()`，却在 close 里写死 `false`——于是"跑满一小时被超时杀"与"正常退出"在错误路径上完全无法区分。加上 stdout 全程只进内存不落日志，一次 25 分钟的僵死派单在日志里**一个字都没有**，我只能靠查进程 CPU 秒数才发现它在空转。修法：软/硬双超时 + 心跳（带"已收输出 X KB"，零输出即僵死信号）+ 正确标记 `timedOut`/`stalled`。**教训：可观测性缺失会让故障归因完全依赖外部手段（查进程表），而那属于运气不属于设计。**
   ⑥ **「配了参数」≠「参数真的生效」**（2026-09-27 漂移重启实测，一个教训值两条）：我设计「漂移→退出码 75→计划任务按 `-RestartCount 3/5min` 自动重启」，并在 selftest 里**断言自启脚本确实配了 `-RestartCount`——该断言通过**。但端到端实测：漂移检测成功退出后，计划任务 **7 分钟内毫无反应**（状态 `Ready`、`LastTaskResult` 空、进程 0）。**必要条件被验证了，充分条件没有。** 原因未查明（事件日志未启用；疑似动作是 run-watcher.cmd 批处理导致 RestartOnFailure 不生效），**不猜**——改为 watcher 自 spawn 脱离替代进程。**教训：断言「配置存在」时必须同时问「它在目标环境下真的生效吗」；两者之间隔着运行时行为，只有端到端能证。**
   ⑦ **状态采集的时机本身就是正确性的一部分**（同一轮实测发现的第三个缺陷）：漂移指纹基线原本在 `await runOnce()` **之后**采集。后果两层，第二层更阴——① 首轮派单期间（实测跑过 28 分钟）完全没有漂移检测；② 首轮结束后会把**改后**的指纹记成基线，**这次改动被静默接受**，正是本机制要防的「看似正常、实则跑旧代码」。修：指纹必须在任何派单动作之前采集，并加断言锁死「指纹早于首次 dispatch 调用」。**教训：防漂移机制自身若初始化太晚就成了摆设——而且是安静地失效。**
