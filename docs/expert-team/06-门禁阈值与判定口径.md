# 06 · 门禁阈值与判定口径

> 本文件解决「7 道门禁只有名词、没有阈值」的老问题：门禁一词不可判定，体系就退化成流程装饰。
> 阈值唯一事实源是 `raci/门禁阈值.csv`；本文件解释用法、口径与人工/自动的分界。

## 1. 为什么要有阈值

原 04 文件里门禁 3~7 的判定物是「逃逸率、自动化覆盖、SLO、高危未修、错误预算」等**裸名词**——没有数值就没有判定，
「任一不过不进下一阶段」这句话在实践中不可执行，评审只能凭感觉。本文件给每道门禁配上**可核对的阈值 + 证据 + 自动化程度**。

## 2. 阈值总表（口径源：`raci/门禁阈值.csv`）

| # | 门禁 | A（人类） | 关键阈值（任一不满足即不通过） | 自动化程度 |
| --- | --- | --- | --- | --- |
| 1 | 产品入场 | 首席产品 | AC 可测率 100%；数据分级率 100%；涉 PII 须 PIA 已启动；影响面>3 模块或>5 人日须拆期+PMO 评审 | 半自动 |
| 2 | 开发入场 | 首席架构 | 架构决策必有 ADR；接口变更必有契约与兼容策略；SAST 新增高危(CVSS≥7.0)=0；PII 字段标记+PIA 编号 | 半自动 |
| 3 | 测试门禁 | 测试治理首席 | P0 逃逸=0；功能逃逸率≤2%；核心链路覆盖≥70% 且变更行≥60%；四类合规用例各≥1 且通过 | 半自动 |
| 4 | 性能门禁 | 性能可靠首席 | 关键接口必须声明 SLO；1.5×峰值下 P99 劣化≤20%；错误率<0.1%；水位≤70% | 半自动 |
| 5 | 安全门禁 | 安全首席 | 高危(CVSS≥7.0)未修=0；密钥扫描命中=0；新增高危 CVE 无豁免不得发布；新接口须鉴权评审 | **高** |
| 6 | 合规门禁 | 合规首席/个保负责人 | 涉 PII 变更 PIA 覆盖=100%；新增数据项分级完成=100%；四项用户权利流程可演示；等保/密评有备案与计划 | 半自动 |
| 7 | 发布门禁 | DevOps首席 | 错误预算 burn rate<100%；回滚预案齐备且演练≤90 天；面向用户发布须灰度；ADR/Runbook/API 文档已归档 | **高** |

> 「高」= 阈值判定可完全机械执行；「半自动」= 取数/统计可脚本化，实质判断仍需人判。**没有一道门禁是全自动放行**——
> 阈值只决定「是否需要人类签字」，不代替人类签字，这与「一事一A、Agent 不放行」不冲突。

## 3. 一事一A 的修正

原 04 文件里门禁 1 写「产品+合规」两个 A，违反体系第一原则（共享 A 等于无 A）。现修正为：

- 门禁 1 **A = 首席产品**（准入决定权）；合规为 C，出具「涉 PII / 等保范围 / 分级」前置结论；
- 门禁 2 **A = 首席架构**（原为空缺，13-架构治理卡未认领，已补）；
- 门禁 6 **A = 合规首席/个保负责人**（名册中为同一人 E-019，文档不得拆成「合规首席 + 个保负责人」两个角色）。

## 4. 术语与命名（唯一口径）

| 概念 | 规范写法 | 禁止的变体 |
| --- | --- | --- |
| 跨域仲裁机构 | 技术治理委员会 | 技术治理委员会、技术治理委员会 |
| 专家建议四态 | 建议批准 / 有条件 / 驳回 / 需人工 | 批准（仅限人类签批结论） |
| 人类签批四态 | 批准 / 有条件批准 / 驳回 / 需人工 | 建议批准 |
| 风险档位 | 低 / 中 / 高 | 低-中、低-高、高危（跨档区间） |
| 升级链路 | 人类首席 → 技术治理委员会 → CTO/法务/安全官 | 止于首席 |
| 升级对象命名 | 用名册职位全称（如「测试治理首席」） | QA首席、性能首席、移动首席、财务合规（名册中不存在） |

校验脚本会检查以上禁用变体与「职位是否存在于名册」，避免再次漂移。

## 5. 门禁判定在体系里的位置

事件驱动派单（`scripts/autodispatch-watcher.mjs`）把变更文件路径交给 router，
router 先按 `raci/路径路由规则.csv` 强制加派专家，再由**该域 A 所属专家**按上表给出门禁判定；
命中「高」风险规则的条目，其结论必须含对应门禁判定，缺证据则结论自动降为「需人工」。
人类签批时，审批单需回填门禁结论与证据链接（`runbook/审批记录.md`）。

## 6. 门禁 7（发布）的前置项清单

**为什么单列一节**：2026-09-28 `expert/20-docs` 在 `DSP-20260928-1228-01` 中把
「核对记录缺失」列为**门禁 7 不通过**的依据。助手复核认为这是**次序倒置**，理由：

> 核对记录是**复核动作的产物**，而复核发生在评审结论产生**之后**。
> 没有复核就没有门禁 7 通过，没有门禁 7 通过就不必复核——成了死循环。

处置：**不改专家结论**（原话留存），改为在本节明确各道门禁的**前置项归属阶段**。

| 阶段 | 必须齐备 | 判定者 |
| --- | --- | --- |
| 评审**中** | 专家结论块（四态/严重度/数据缺失齐备） | R 专家 Agent |
| 评审**中** | 派单台账有对应行（含 R/C/派发/结论摘要） | 脚本（fail-closed 门） |
| 签批**时** | 人类 A 的签批结论 + 决策依据 | 人类 A（**只有人类能落终态**） |
| 复核**后** | 双方核对台账有对应行（专家原话 × 复核结论并列） | 助手自动复核 |
| 发布**前** | 上述四项 + 六项检查全绿 + 无「无人处理的挂账」（validate 第 17 节） | CI + 人类 A |

**即：「核对记录齐备」是发布前检查，不是评审中检查。**
若人类 A 认为原判更合适，请改回本节——**助手不单方面改动门禁语义**。

## 7. 复核后「决定不采纳」的三项（决定记录）

以下三项由专家提出、助手**逐条复核后决定不采纳**。集中记录于此以免散落，
并各自写明**依据**与**重启条件**（触发即须重议，不是永久否决）。

### 7.1 指纹是否扩到子进程型 gate 脚本 —— 不采纳

- 专家建议（`expert/18-security` @ `DSP-20260928-1149-01`）：把 `guard-audit.mjs` /
  `validate-expert-team.mjs` 等纳入 `sourceFingerprint` 覆盖。
- **不采纳依据（实测）**：watcher **没有任何项目模块的静态或动态 import**；
  gate 脚本全部是**每轮 spawn 子进程**执行，每次从磁盘重载，**不存在陈旧**。
  纳入会让每改一次门禁脚本就消耗一次重启深度，而深度超限的后果正是降级模式
  ——**为不存在的风险消耗真实的安全余量**。
- 依据落地位置：`scripts/autodispatch-watcher.mjs` 的 `sourceFingerprint` JSDoc；
  `selftest §24.10` 双向断言（真出现 import 时必须扩大；不许顺手扩大）。
- **重启条件**：若将来 watcher 改为 `import` 任何项目模块，该建议立即重议。

### 7.2 CI 是否引入独立密钥扫描（gitleaks） —— 暂不采纳

- 专家建议（`expert/18-security` @ `DSP-20260928-1149-01`，其自定时限为 1 个月，非阻塞）。
- **不采纳依据**：门禁流水线本身就是被点名的**供应链攻击面**；引入它等于
  **新增一个外部 action 依赖** ＋ 一个**待确认的许可限制**，
  换取的只是「比现有 `guard-audit --strict` 正则更全的规则」。不划算。
- 依据落地位置：`docs/expert-team/04-编排与门禁.md`「门禁 5 的已知取舍」小节。
- **重启条件（须同时满足）**：① 人类 A 确认许可可用于本组织；
  ② action 以 SHA 锁定；③ 与现有 `guard-audit --strict` 并行跑一段时间不误报。

### 7.3 核对记录「挂账」的判定方式 —— 已采纳并加门

- 这项**不是**不采纳，是本轮**新增**的机制：核对记录里凡「未修/挂账」的子句，
  自身必须带 ✅ 已闭环标记，否则 `validate` 第 17 节报红。
- 起因：核对记录里曾有 **7 条**写着「未修」而实际早已完成，助手自己差点信了。
- 诚实边界：该检查**只能**发现「无人处理的挂账」；**谎称已闭环它抓不到**
  ——那要靠人核 commit 是否真在 `git` 历史里。
- 判定逻辑：`scripts/lib/crosscheck-hang.mjs`；反向测试（插假行→报红→移除→绿）已跑通。
