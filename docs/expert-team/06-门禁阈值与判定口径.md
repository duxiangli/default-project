# 06 · 门禁阈值与判定口径

> 本文件解决「7 道门禁只有名词、没有阈值」的老问题：门禁一词不可判定，体系就退化成流程装饰。
> 阈值唯一事实源是 `raci/门禁阈值.csv`；本文件解释用法、口径与人工/自动的分界。

## 1. 为什么要有阈值

原 04 文件里门禁 3~7 的判定物是「逃逸率、自动化覆盖、SLO、高危未修、错误预算」等**裸名词**——没有数值就没有判定，
「任一不过不进下一阶段」这句话在实践中不可执行，评审只能凭感觉。本文件给每道门禁配上**可核对的阈值 + 证据 + 自动化程度**。

## 2. 阈值总表（口径源：`raci/门禁阈值.csv`）

| # | 门禁 | A（人类） | 关键阈值（任一不满足即不通过） | 自动化程度 |
| --- | --- | --- | --- | --- |
| 1 | 产品入场 | 首席产品 | AC 可测率 100%；数据分级率 100%；涉 PII 须 PIA 已启动；影响面>3 模块或>5 人日须拆期+PMO 评审 | 半自动 |
| 2 | 开发入场 | 首席架构 | 架构决策必有 ADR；接口变更必有契约与兼容策略；SAST 新增高危(CVSS≥7.0)=0；PII 字段标记+PIA 编号 | 半自动 |
| 3 | 测试门禁 | 测试治理首席 | P0 逃逸=0；功能逃逸率≤2%；核心链路覆盖≥70% 且变更行≥60%；四类合规用例各≥1 且通过 | 半自动 |
| 4 | 性能门禁 | 性能可靠首席 | 关键接口必须声明 SLO；1.5×峰值下 P99 劣化≤20%；错误率<0.1%；水位≤70% | 半自动 |
| 5 | 安全门禁 | 安全首席 | 高危(CVSS≥7.0)未修=0；密钥扫描命中=0；新增高危 CVE 无豁免不得发布；新接口须鉴权评审 | **高** |
| 6 | 合规门禁 | 合规首席/个保负责人 | 涉 PII 变更 PIA 覆盖=100%；新增数据项分级完成=100%；四项用户权利流程可演示；等保/密评有备案与计划 | 半自动 |
| 7 | 发布门禁 | DevOps首席 | 错误预算 burn rate<100%；回滚预案齐备且演练≤90 天；面向用户发布须灰度；ADR/Runbook/API 文档已归档 | **高** |

> 「高」= 阈值判定可完全机械执行；「半自动」= 取数/统计可脚本化，实质判断仍需人判。**没有一道门禁是全自动放行**——
> 阈值只决定「是否需要人类签字」，不代替人类签字，这与「一事一A、Agent 不放行」不冲突。

## 3. 一事一A 的修正

原 04 文件里门禁 1 写「产品+合规」两个 A，违反体系第一原则（共享 A 等于无 A）。现修正为：

- 门禁 1 **A = 首席产品**（准入决定权）；合规为 C，出具「涉 PII / 等保范围 / 分级」前置结论；
- 门禁 2 **A = 首席架构**（原为空缺，13-架构治理卡未认领，已补）；
- 门禁 6 **A = 合规首席/个保负责人**（名册中为同一人 E-019，文档不得拆成「合规首席 + 个保负责人」两个角色）。

## 4. 术语与命名（唯一口径）

| 概念 | 规范写法 | 禁止的变体 |
| --- | --- | --- |
| 跨域仲裁机构 | 技术治理委员会 | 技术治理委员会、技术治理委员会 |
| 专家建议四态 | 建议批准 / 有条件 / 驳回 / 需人工 | 批准（仅限人类签批结论） |
| 人类签批四态 | 批准 / 有条件批准 / 驳回 / 需人工 | 建议批准 |
| 风险档位 | 低 / 中 / 高 | 低-中、低-高、高危（跨档区间） |
| 升级链路 | 人类首席 → 技术治理委员会 → CTO/法务/安全官 | 止于首席 |
| 升级对象命名 | 用名册职位全称（如「测试治理首席」） | QA首席、性能首席、移动首席、财务合规（名册中不存在） |

校验脚本会检查以上禁用变体与「职位是否存在于名册」，避免再次漂移。

## 5. 门禁判定在体系里的位置

事件驱动派单（`scripts/autodispatch-watcher.mjs`）把变更文件路径交给 router，
router 先按 `raci/路径路由规则.csv` 强制加派专家，再由**该域 A 所属专家**按上表给出门禁判定；
命中「高」风险规则的条目，其结论必须含对应门禁判定，缺证据则结论自动降为「需人工」。
人类签批时，审批单需回填门禁结论与证据链接（`runbook/审批记录.md`）。
